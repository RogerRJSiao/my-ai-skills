# 改善提案表 撰寫skill

一份可重複使用的「改善提案表」撰寫與檢查邏輯，多份實際提案(數位轉型自動化、ERP編號改善、教育訓練教材更新、PBI報表SQL優化等)歸納而成。

## 核心架構（四段式，缺一不可）

```
提案名稱(20字以內)　【分類標籤，如：品質/效率/成本，可複選用「/」分隔】

現狀缺失
【背景/制度說明】。【目前做法或侷限】，【造成的具體風險或成本】。

改善內容
為了【改善目的】，透過【工具/方法】，可完成：
1. 【做法一(白話標題)】：【專業說明+白話比喻】。
2. 【做法二】：...
3. 【做法三】：...
4. 【做法四，通常是「命名/版控/文件化」類的收尾】：...

相關檔案／連結：(選填)
- 連結、GitLab work item、MIS維護單號等
```

## 撰寫「現狀缺失」的公式

固定包含三層，缺一層審核者容易看不懂為什麼要改：
1. **背景/制度**：為何存在這件事(哪個系統、哪個流程、哪個規定)
2. **現行做法的侷限**：具體指出「先做A才做B」這種沒效率或有風險的順序/缺口
3. **造成的後果**：遺漏、耗時、無法辨識、逾時失敗等，能量化就量化（例如附上錯誤訊息、單號）

寫法上要**精簡**：優先用一到兩句話講完，避免同一件事講兩次（審核者沒有耐心看重複描述）。若使用者提供截圖或錯誤訊息（如`57014: canceling statement due to statement timeout`），可直接引用錯誤代碼精簡帶過，**不要**寫「如附圖：」這種依賴外部圖片才能理解的贅詞——文字本身要能獨立說明清楚。

## 撰寫「改善內容」的公式：專業詞彙 + 白話科普

這是本skill最重要的技巧，直接套用即可：

1. 每一點先給一個**白話小標題**（括號內），再寫專業做法。
   - 範例：`源頭篩選優化(篩選交給資料庫先做)`
2. 專業詞彙第一次出現時，**用生活化比喻或極簡白話解釋**，但**不需要每次都展開成長篇比喻**——比喻只用一次，之後可以簡化只留關鍵詞。
   - 範例：WHERE子句 → 「先跟倉庫說好要哪些貨，直接送需要的」
   - 索引(index) → 「類似目錄，可快速定位資料」
3. **避免使用過度抽象或英文直譯的技術詞**，優先換成更好懂的中文詞：
   - 「下推」→ 建議改「源頭篩選」或視審核對象保留「查詢下推(Predicate Pushdown)」
   - 詞彙選擇原則：面向非技術主管用最白話的詞；面向IT/工程背景審核者可保留專業詞+英文對照
4. 若某個限制是「即使做了A優化，仍可能受B因素影響」，務必誠實寫出來，不要為了讓提案內容看起來完美就省略限制條件。
   - 範例：`CommandTimeout`只能延長用戶端等待時間，仍會受資料庫伺服器本身的逾時設定影響。
5. 分點數量：**建議3~4點**，最後一點通常收斂在「文件化/命名規則/版控紀錄」，讓提案有「制度化、可長期維護」的收尾感，而非只是一次性修補。

## 台灣用詞檢查清單

送出前用這份清單核對，避免混入大陸用語：

| ❌ 避免 | ✅ 台灣慣用 |
|---|---|
| 数据/数据库 | 資料/資料庫 |
| 文件 | 檔案 |
| 超时 | 逾時 |
| 软件 | 軟體 |
| 硬件 | 硬體 |
| 优化 | 優化（此詞兩岸皆通用，可保留） |
| 视频 | 影片 |

不確定的詞彙，優先採用使用者原始文件、公司內部系統畫面(如BPM、ERP、PBI介面)中出現的既有用語，不要自創替代詞。

## 提案類別自動推薦（依正式申請表下拉選單）

正式的「改善提案表」系統中，內容代碼／分類欄位共有9種選項（來源：實際申請表下拉選單截圖），**不是只有品質/效率兩種**，請依提案內容判斷後主動推薦最合適的1~2個，而非預設套用品質或效率：

| 分類 | 適用情境判斷依據 |
|---|---|
| **效率** | 縮短作業時間、自動化流程、減少人工追蹤/等待、程式或查詢效能優化(如SQL、報表載入速度) |
| **品質** | 提高資料正確性/一致性、減少遺漏或錯誤、提升教材/文件內容的正確性與時效性 |
| **成本** | 明確能換算成金額節省(人力工時、設備、耗材、外包費用等)，且提案表本身有「效益分析」欄位需填年節省金額 |
| **生產** | 涉及產線、製程、產能、生產排程、良率等直接與生產作業相關的改善 |
| **環境** | 節能減碳、廢棄物減量、環保法規相關、能源使用效率 |
| **安全** | 降低職業災害風險、設備操作安全、資安/系統存取安全 |
| **衛生** | 工作場所衛生、食品/化學品相關衛生管理 |
| **防災** | 消防、天災應變、緊急應變機制、備援/備份機制(可與效率並列，如系統備份自動化) |
| **其他** | 上述皆不符合時使用，避免勉強套用不合適的分類 |

**推薦原則**：
- 先判斷提案的**主要動機**（省時間？省金錢？防止資料錯誤？防止意外？），主要動機對應的分類放第一位
- 允許複選（如「效率/品質」「效率/防災」），但**不建議超過2個**，避免分類失焦
- 若提案內容同時具備「效益分析」段落且能量化金額，即使主要動機是效率，也應提醒使用者可加填「成本」分類
- 若使用者提供的草稿已自行標註分類，仍要對照本表快速檢查是否合理，不合理才提出建議，不要每次都重新推翻使用者的判斷

## 正式申請表的完整欄位（供對照，非本skill撰寫範圍）

正式系統另有以下欄位，本skill主要協助撰寫「提案名稱」「現狀缺失」「改善內容」三大文字區塊；以下欄位若使用者要求也可協助但非預設輸出範圍：

- 提案日期、填表人、提案人、相關部門與參與比率
- **效益分析**：改善前計算、改善後計算、年節省金額計算、金額(元) — 若使用者要填這塊，需請使用者提供具體數據，不可捏造金額
- 與QCC活動主題相關(是/否)、QCC主題編號
- 職責關係代碼、本案是否實施
- 上傳佐證檔案

## 相關資料夾慣例（若使用者要求歸檔到repo）

若使用者要把提案素材整理進repo（如`improvement-proposal-draft`專案），依素材性質分兩類，不要混放：
- `materials/`：**改善前**的佐證素材，用來證明問題存在（程式碼、SQL、截圖、CHANGELOG、錯誤訊息截圖等）
- `deliverables/`：**改善後**的實作成果，證明提案已落地產出的最終檔案或連結（最終pbix、Flow匯出檔、更新後的PPT等）

兩者都以「提案主題」命名子資料夾，不用檔案類型分類。若只有SharePoint連結、尚無實體檔案，`deliverables/`底下可先放一份`README.md`記錄連結，待日後有實體檔案再補上。

## 常見排版/格式檢查（每次交稿前必查）

送出最終稿前，逐項檢查以下容易被忽略的細節：

- [ ] 編號後面是否有加空格（`1. xxx`而非`1.xxx`），全份文件格式一致
- [ ] 是否殘留個人筆記/草稿標記，例如`[不寫]`、`[備用]`、`TODO`等字樣——**這類標記若出現在同一份草稿中超過一次仍未刪除，要主動提醒使用者**，不要每次都當作全新問題重複同樣的建議而不指出「這是第N次出現」
- [ ] 分類標籤是否符合提案實際性質，並對照「提案類別自動推薦」表確認沒有更合適的分類被漏掉（分類共9種：效率/品質/成本/生產/其他/環境/安全/衛生/防災，不要只在品質/效率兩者間打轉）
- [ ] 若程式碼中有分類註解（如Power Query的段落註解），改善內容提及「加上註解分段」時，列出的分類名稱要跟程式碼實際的分類**逐一對照**，不能漏列或漏看
- [ ] 相關連結/單號格式一致，且提醒使用者自行確認連結有效性（Claude無法驗證外部連結是否可開啟）

## 工作流程建議

1. 使用者提供技術素材（程式碼、SQL、截圖、系統操作紀錄、CHANGELOG等）→ 先看這些素材找出「差異」或「問題點」，用表格整理給使用者確認理解正確
2. 依「現狀缺失」公式草擬第一版
3. 依「改善內容」公式（專業詞彙+白話）草擬分點
4. 主動跑一次「台灣用詞檢查清單」與「常見排版檢查」，即使使用者沒要求也要做
5. 若使用者反覆要求「簡化」，每次只精簡字句、不要刪減必要的三層邏輯（背景/侷限/後果），避免簡化到讀者看不懂為什麼要改
6. 使用者確認「OK」或「不需要調整」後，才視需要協助轉存Word檔（需另外使用docx skill）

## 這個skill不做的事

- 不會自動判斷提案的「分類標籤」對錯——只能依內容性質給建議，最終分類由使用者/審核制度決定
- 不會驗證SharePoint、GitLab等外部連結是否有效
- 不會捏造沒有在使用者提供素材中出現的技術細節或數據
