# Power BI (.pbix) 版本命名與 CHANGELOG 維護

一套用來持續記錄 pbix 檔案版本演進的規則與工作流程。目的：讓「檔名」「CHANGELOG 表格」「實際 SQL/欄位邏輯改動」三者永遠對得上，避免半年後回頭查不出「這個版本到底改了什麼」。

## 何時使用

- 使用者要上線/發布新版 pbix，需要決定新檔名(版號該跳主版號還是次版號)
- 使用者上傳了 pbix 檔案、或儲存位置的**截圖**(如 SharePoint、知識中心的檔案清單，含檔名、修改時間、修改者、建立者等欄位)，要求整理或核對版本紀錄
- 使用者要新增/修改 CHANGELOG.md 的版本紀錄
- 使用者問「這次改動算大改還是小改」「欄位模式要不要跳版號」等版控判斷問題

## 參考資料來源

處理任何版本紀錄任務時，優先蒐集以下兩類資訊，缺一都要主動詢問或提醒使用者補充：

1. **pbix 檔案本身**：檔名（依命名規則可反推版號、欄位模式）、檔案內部的 Power Query / M 語言查詢邏輯（SQL 語句、參數設定、索引鍵使用情況、欄位清單）。若使用者上傳了 pbix，檢查其 M 查詢與參數，確認實際改動內容與使用者描述的是否一致。
2. **儲存位置的截圖**：例如知識中心/SharePoint 的檔案清單畫面，通常包含「名稱」「修改時間」「修改者」「建立者」「建立時間」等欄位。這些是判斷「上線日」「實際版本是否已存在」「是否有未同步的版本」的第一手依據——**上線日期一律以此類截圖或系統紀錄的實際時間為準，而非使用者口頭說的預計時間**。

若兩者之一缺失（例如只有截圖沒有 pbix，或只有 pbix 沒有截圖），可以先用手邊資料處理，但要明確告知使用者：「日期/檔名已用截圖核對」或「SQL 改動內容未核對到實際 pbix，以你的描述為準」。

## 命名規則

```
{報表名稱}v{主版號}.{次版號}_{欄位模式}.pbix
```
（`報表名稱` 依專案而定，例如「三角與非三角合併」；已確定的專案請延用既有前綴，不要自創新前綴）

### 版號判斷標準

| 改動類型 | 判斷依據 | 版號變化 |
|---|---|---|
| **主版號 (Major)** | 資料模型結構改變（新增/移除資料表關聯、量值邏輯大改）、參數機制新增或改變（如新增/移除編輯參數）、資料來源整個更換 | v(n) → v(n+1)，次版號歸零 |
| **次版號 (Minor)** | SQL 查詢優化（如加索引鍵）、欄位增減、bug 修正、視覺化調整 | v(n).(x) → v(n).(x+1) |

**邊界情況原則**：如果一次改動「新增了分支/模式」（例如本例的 full/finance 欄位模式分支），但底層資料模型與既有參數機制未變動，預設歸類為次版號改動 —— 但務必在 CHANGELOG 該筆紀錄的備註欄寫清楚判斷理由，避免日後被誤認為版控邏輯有漏洞。若使用者對此有不同意見，以使用者最終判斷為準。

### 欄位模式（依專案擴充）

欄位模式的命名應反映「使用對象」或「資料範圍」，且一旦定義後盡量維持字面意義穩定（即使該模式未來擴充欄位，只要邏輯性質不變，仍用原本的名稱，不因擴充而改名）。範例：
- `full`：完整欄位版本，延續原始設計
- `finance`：依特定部門（如財務）需求篩選出的精簡欄位版本，通常附帶「保留未來擴充空間」的設計（例如 PQ 中保留註解掉的欄位，方便日後啟用）

### 版號同步規則（可依專案調整，但需明確寫入文件）

若專案決定「多個欄位模式版號永遠同步升級」：
- 只要任一模式有改動，**所有模式的檔名版號都要一起跳**，即使某個模式的內容完全沒變
- 好處：任何時候看到版號，就能直接對照其他模式是否為同批次；避免「full v3.1 對應 finance 哪一版」的疑問
- 這條規則務必寫在 CHANGELOG.md 的命名規則說明區，不要只放在對話紀錄裡

## CHANGELOG.md 格式

每次協助使用者更新版本紀錄時，套用以下結構（可參考 `references/changelog_template.md`）：

1. **檔案位置**：說明實際存放路徑（如知識中心/資料夾路徑）
2. **命名規則**：完整命名格式 + 主/次版號定義 + 各欄位模式定義（含 latest 版本標記）
3. **釋出版本表格**，欄位建議包含：
   - 版本（含欄位模式後綴）
   - 上線日（以截圖/系統實際時間為準；若為預定日，需標註「預定」並提醒之後回來核實）
   - 功能說明（重要改動）：具體寫出「做了什麼」，不要只寫「優化」二字帶過——要講清楚優化的對象（SQL/欄位/參數等）
   - 其他（備註）：判斷理由、與其他版本的關聯、原檔名沿革、可擴充性說明等

### 撰寫備註時的檢查清單

每次新增或修改一筆版本紀錄後，自我檢查以下幾點（這是根據實際維護經驗歸納的常見疏漏）：

- [ ] 欄位模式的定義（如 full/finance）是否與較早版本的功能說明**一致**？（例：若 v2 說明是「合併兩張表取出 47 欄」，欄位模式定義裡的「47 欄」來源說明要對得上，不能只寫其中一張表）
- [ ] 若某個版本同時做了「SQL/索引優化」與「欄位縮減」兩件事，備註是否兩者都有提到？不要讓其中一項被另一項蓋過（例如只寫「縮減欄位」卻漏了「同步做了索引優化」）
- [ ] 欄位數字大幅變動時（例如 75 欄→47 欄），是否在備註說明了原因？不要讓讀者需要自行猜測「為什麼多接一張表欄位反而變少」
- [ ] 若使用「同上一列」「同上」等指代用語，確認用字正確 —— 中文表格中「欄/行」是直向分類、「列」是橫向的一筆記錄，兩者不可混用
- [ ] 若本次改動新增了分支邏輯（如欄位模式），是否有寫清楚「為何歸類為次版號而非主版號」的判斷理由
- [ ] 上線日是否為預定日？若是，提醒使用者上線後要回來確認並更新為實際日期

## 工作流程

1. 使用者描述本次改動（或上傳 pbix / 截圖）→ 先釐清：這次改動的具體內容是什麼（SQL？欄位？參數？資料模型？）
2. 對照「版號判斷標準」，建議應跳主版號還是次版號，並說明理由
3. 若使用者已有既存 CHANGELOG.md，先讀取並檢查既有格式與規則是否與這次改動一致（例如：欄位模式是否延續已定義的名稱、版號同步規則是否有遵守）
4. 依「CHANGELOG.md 格式」新增/修改該筆版本紀錄，並跑過上方「撰寫備註時的檢查清單」
5. 產出修改後的完整 CHANGELOG.md，並向使用者具體指出這次新增/修正了哪幾點（不要只丟出整份檔案，要說明改了什麼、為什麼這樣改）
6. 若使用者提供的截圖與 pbix 檔名/內容有落差（例如截圖上的檔名版號跟本次討論的規則對不上），主動指出落差，不要默默忽略
